# P Discovery 批量研究 v0.3：选题目录与质量优先的执行方案

> 状态：提案（尚未自动执行研究，尚未切换 P Atlas 发布目录）。选题来源包括现有的公开研究资产与近期产品探索方向。
>
> 核心分工：**选题目录决定研究什么；Codex + `p-discovery` Skill 决定怎样研究；P Atlas 仅消费已发布结果。**
>
> 参考：`catalog/p-discovery-backlog.v0.3.json`。它包含 12 类、72 个**新的候选主题**，与 `catalog/p-atlas-topics.v0.1.json` 的主分支主题和 PR #4 的 v0.2 主题去重。上述 72 个主题全部标记为 `candidate`，不代表存在已确认的可能性地图。

## 1. 必须区分三个目录

| 目录 | 内容 | 功能 | 是否公开为已研究 |
| --- | --- | --- | --- |
| Research backlog | 候选主题与研究范围、优先级、批次 | 定义下一步研究什么 | 否 |
| Outputs | 已交付的 `possibilities.json` / `possibilities.md` / 证据记录 | P Discovery 的知识资产 | 必须先通过审核 |
| P Atlas catalog | 已发布或明确待研究的主题入口 | 阅读器的可见主题清单 | 仅 `ready` 可看地图 |

**候选主题不是 P。** 主题目录可在研究前以领域分类；每个主题内部必须仍然先收集资料和发现 P，再去重补漏，最后分类。不允许给主题套用预制 P 分类表。

## 2. 主题的最小质量契约

进入批次前，每个候选必须确认：
- 一个可独立研究的对象（产品 / 框架 / 工具 / 技术 / 有边界的方法），不可只写「全部 AI」「所有软件」。
- 研究范围与排除范围；具体产品版本/平台约束由研究阶段查证，不凭主题名称臆测。
- 与现有 v0.1 和 v0.2 目录无同义重复。相关但粒度不同的主题可以保留，但要记录关联。
- 至少能找到可信的资料发现入口（官方文档、项目 README、标准、真实示例等），否则暂列 `blocked` 等待补充。
- 不以 P 数量、来源数量或者完成速度为发布依据。

建议状态：`candidate → selected → researching → review → accepted → published`；中途允许 `blocked` 或 `rework`。这是一套研究队列状态，不修改现有 P 的证据状态含义。

## 3. 资料发现与检索：最需要做好的环节

每个研究 worker 都执行现有 Skill。搜索过程至少有三条互补路线，不需要强制来源配额：
1. **官方路线：** 首页/用途说明、指南、Reference、release/compatibility、官方 sample/gallery，用来确定实际可支持的能力边界；
2. **使用路线：** 官方真实案例、作者项目、完整开源应用、研究/社区实践，提取他人做成的用户结果，注明「演示 / 自报 / 已部署 / 已复现」的证据强度；
3. **扩展路线：** 官方插件目录、可选集成、第三方生态，明确所需组件/账号/付费/环境，不将其归给核心功能。

当某个来源类型发现不足时，要有意识改变查询策略；当结果仍不全时，记录覆盖缺口或阻断，而不是生成似是而非的 P。补漏允许模型提出搜索关键词，却不能把推断直接标为已证实。

每条 `source_supported` P 至少要有原文直接支持其结果；短摘录匹配只是一道结构检查，不能代替语义判断。源码类引用优先固定 commit 并保留行号；网页要记录研究日期、具体位置及必要的版本限制。引用不可达、页面只有壳、案例无法核查等必须标记。

## 4. 研究批次：小批量、独立输出、质量门禁

先运行三个候选小批次。每批 6 个主题，**最多 2 个并行研究 worker**（可逐一串行，质量优先）；即使工具支持更多并发，也不要在试点前一次性发起几十个。不同 worker 不能写同一个目录或改 Skill。

| 批次 | 主题（有意跨域） | 验证重点 |
| --- | --- | --- |
| B01 | PydanticAI、MLX LM、ComfyUI、Tauri、Shiny、RSSHub | 能否跨 Agent、本地模型、创作、桌面软件、数据应用与信息订阅稳定研究 |
| B02 | LlamaIndex、Firecrawl、browser-use、llama.cpp、Remotion、Qdrant | 检索与执行能力的粒度、框架和生态边界 |
| B03 | Langfuse、vLLM、OpenHands、LTX Video、Astro、Home Assistant | 评测、模型服务、编程代理、视频和日常自动化的真实结果 |

研究产物必须独立落盘在 `outputs/<slug>/`：
- `possibilities.json`：标准 P、证据及类别；
- `possibilities.md`：面向读者的可用地图，和 JSON 同步；
- `validation-report.txt`：实际执行的检查与未验证项；
- `discovery-log.md`：检索/归一化/补漏/停止原因；
- `source-coverage.json`：来源类型、取回/失败/拒绝记录、时间/版本和取回凭证。

不要修改此前 38 个主题对应文件，不要重新生成旧研究，不要让研究 worker 自己设定其成果为 `reviewed`，也不要自动切换 P Atlas catalog。

## 5. 每个主题的验收标准

### 自动可检查
- 复用 `.agents/skills/p-discovery/scripts/validate.py`；
- 每个确认 P 的证据引用/原文/链接定位一致，Markdown 与 JSON 对应，不存在非法引用或静默删去条件；
- 来源时间、版本及插件归属可追踪；
- `git diff --check`、研究校验脚本、Skill 既有单元回归通过；
- 研究失败或部分完成时保留原始工作与失败报告，但不得标为 ready。

### 审阅者必须判断
- 重要的 P 是否是用户能获得的结果，而不是 API 名称、一个按钮或无意义的组合；
- 最重要的 P 是否真能由证据推断，是否遗漏关键前提；
- 官方、生态、用户场景是否都得到适当覆盖（缺失要说明原因）；
- 是否有重大缺口、错误核心/扩展归属、无依据价格/版本承诺；
- 以用户角度浏览地图，是否获得了此前不知道的可行选择。

建议风险导向抽查每个主题至少 5 个关键 P，或约 20%（取较高的适当值），再审视所有高度敏感/有争议的产品能力。**该数值是试运行审阅工作量建议，不是独立研究质量的证明。** 发现重大错误则该主题回到 `rework`；不存在全批次自动通过。

## 6. Codex 调度：先靠 Skills 和 Git，暂时不重建 Agent Harness

MVP 由 Codex 读取候选目录，选择 B01，逐项调用现有 `p-discovery`；允许最多两个独立任务并行。每个任务都应写自己的 `outputs/<slug>/`，并保持审查日志和生成结果可追踪。可以让一个 coordinator 汇总检查，但不得用其自评取代独立人工验收。

完成 B01 后：
1. 自动验证各主题结构与引用，并生成批次汇总；
2. 对证据和覆盖做独立审阅，明确 `accepted/rework/blocked`；
3. 通过的主题进入一个研究 PR；
4. 合并后将被接受的主题纳入 P Atlas 正式发布目录；
5. 先做完整 6 主题的前端浏览器回归，再触发线上部署；
6. 分析 B01 结果，再决定是否启动 B02。

一个批次内遇到失败只标记失败主题，不让坏成果污染整批；保留已经完成的可核查内容。

## 7. 长期维护：如何扩张候选目录

建议每隔一轮从四种来源发现新候选：
- **用户目标反推：** 哪些事情想做却不知道用什么工具；
- **成熟生态：** 相关官方产品/框架、扩展目录、Awesome 清单、开源真实案例；
- **已发现 P 的外部依赖：** 对某个主题反复出现的第三方工具，再决定它是否值得独立成为主题；
- **新出现的问题域：** 产品真实使用者提出的问题与未覆盖的用途类型。

新主题先成为 `candidate`，去重和限界后才进入批次。目录扩张与 P 地图生产是两条不同任务，不能把几百个主题无审阅地一次性投入研究队列。

## 8. 对现有仓库的兼容与发布顺序

现有主分支正式目录为 v0.1 的 20 主题；PR #4 含 v0.2 的 18 新主题，但在本提案编写时尚未合并。候选目录不应该假装这 18 个已经在线发布。下一轮研究可先在独立分支进行，但合并研究资产前要对照 PR #4 重新去重及确认合并顺序。

不修改现有 `apps/atlas`、`apps/web`、P Discovery Skill。待首次批次验证后再考虑开发极简批量 CLI 和内容发布按钮，而不是先创建复杂调度器。

## 9. 给 Codex 的首轮执行要求

```text
阅读 catalog/p-discovery-backlog.v0.3.json 及 docs/proposals/p-discovery-batch-v0.3.md。
本次仅执行 B01，不开始 B02/B03。
使用现有 p-discovery Skill，不更改研究方法。
最多两个研究任务并行；每个主题独立收集、验证、保留 5 件产物。
优先官方与真实使用案例，不以模型推测扩充已证实结果。
合并归一化 P 后再分类，严格区分核心、扩展和不确定性。
保留检索日志与失败/未覆盖资料，不能虚构引用。
只提交本批输出与批次验收说明；不自动合并 PR，也不改变线上发布目录。
完整验证后给出 accepted / rework / blocked 建议及具体理由。
```

**验收重点：一次批量研究结束后，研究数量增加了，但每项结果仍有可靠来源、适当粒度、清晰边界；不要求某个固定数量的 P。**
