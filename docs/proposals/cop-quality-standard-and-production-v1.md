# COP 质量标准、LangChain 标准样板与稳定生产方案

> 日期：2026-10-02。
> 状态：讨论草案，不是已经生效的 Schema 或产品验收规则。
> 本文定义 COP Studio 自己的质量标准，不声称存在唯一的外部“行业标准 COP”。
> 本轮只制定标准与实施路线；没有修改业务代码、生成流程或已发布 COP。

## 1. 产品判断

标准 COP 不等于字段齐全的 JSON，也不等于一篇带流程图的教程。

建议定义为：

> 面向明确用户，在声明的起点和适用范围内，以一条简洁主线连接关键 Concept 与 Operation，使用户完成可核对的能力成果，并能解释、诊断和迁移到相近问题的知识工件。

核心检验是三件事：

1. 知道做什么、为什么这样做。
2. 按路径真的能做成，而不需要补上未声明的领域知识。
3. 换一个相近问题，知道应该改哪里，以及哪些部分不能直接照搬。

这延续原始规范的 L1 结构有效、L2 操作有效、L3 心智模型有效，不把 L3 降成“有练习和完成按钮”。依据：[COP Specification](/Users/milin/2026/软件开发/COP/cop-studio-development-spec-v1.0/docs/02-cop-specification.md:246)、[Product Vision](/Users/milin/2026/软件开发/COP/cop-studio-development-spec-v1.0/docs/01-product-vision.md:1)。

## 2. 两种“标准”必须分开

| 标准 | 回答什么 | 不能证明什么 |
| --- | --- | --- |
| 数据结构标准 | 工件如何存储、引用、版本化、展示和导出 | 内容是否正确、是否能照做、是否教会人 |
| 内容质量与验收标准 | 什么样的能力路径可以交付；用什么证据证明 | 不能只靠加字段或模型自评分实现 |

应先定义交付物与验收，然后从标准样板中提取最少必要字段。不能反过来把当前 Schema 能表达的范围当成 COP 的全部要求。

全局标准不应绑定 Python、LLM、向量库或特定 API。脚本、命令、数据文件属于软件领域的实现配置；非软件领域也应该能用输入、操作、产物、判断和错误恢复表达相同契约。

## 3. 标准 COP 的九项要求

### S1 · 范围和起点明确

- 声明目标用户、领域边界、非目标和适用条件。
- 声明入场能力、资源与已有环境，不能假设用户已经完成领域 setup。
- Zero State 是“没有未声明的领域前置条件”，不是“用户什么基础知识都没有”。例如可声明会基本 Python，但不能默认为其已配置 LangChain provider。
- 软件领域声明运行环境与已测试版本；有资金、账号、权限或网络要求时说明。

### S2 · Goal 是有价值的能力成果

- 不用“学习/理解某主题”代替完成定义。
- 每个 Goal 指定可观察成果、成功条件和不算成功的情况。
- 有前置 Goal 就明确列出，不伪装成从零独立可做。
- 不为数量指标添加低价值 Goal；覆盖范围少而完整可以合格，范围大而含糊不能。

### S3 · 一条可追溯的默认主线

- 用户能直接找到起点、完整 Main Process、当前位置和下一步。
- 每条路径回溯到声明起点或可进入的 Shared Foundation。
- 前一 Stage 的产物能成为后一 Stage 的输入；持久化、共享对象或重新构造的方式明确。
- Foundation 是知识复用，不是删去 setup 内容或入口。
- 默认路径应是目标用户最常见、最容易复现的工作方式，不只是最短字符数的方式。

### S4 · Stage 是一个闭合的局部任务

每个可执行 Stage 至少回答：

| 项目 | 需要回答的问题 |
| --- | --- |
| 局部目标 | 完成什么，得到什么？ |
| 理由 | 为什么需要这一步，省略会怎样？ |
| 输入与依赖 | 已有对象、文件、配置和前置任务从哪里来？ |
| Concept × Operation | 对什么对象做什么操作，引起什么变化？ |
| 默认做法 | 在哪里创建/修改什么，以什么方式执行？ |
| 输出交接 | 留下什么产物，下一步如何获得它？ |
| 验收 | 什么观察能证明局部目标达成？ |
| 失败恢复 | 哪些常见错误如何区分，如何恢复？ |

纯解释性 Stage 不应被强迫编造命令；可用解释、分类、预测或决策任务验证。但可执行主线不能用“阅读一下”替代必要操作。

### S5 · 概念与操作有因果连接

- Concept 不是名词清单，Operation 不是 API 清单。
- 用户能说清“对哪个对象做了什么，因此产生什么结果”。
- 同一概念在不同 Stage 的含义一致；参数、实例名和函数拼写通常留在 Implementation Detail。
- Mental Model 说明核心对象如何协作、状态如何流动、扩展接在哪里。
- 既避免百科化，也避免只剩可复制代码而无法理解系统。

### S6 · 没有承重的隐藏知识

执行关键知识必须写在当前任务中，或有清晰、可达的前置链接。被声明为入场能力的基础知识不必重复教学。

软件例子：配置来源与优先级、.env 是否加载、工作目录、虚拟环境、对象生命周期、文件生成位置、工具能力要求、请求成本、输出如何检查。

“没有隐藏知识”不等于全部细节同时显示；它要求必要信息存在、能找到、和当前任务关联。用户不应为了完成默认主线再自行搜索缺失的必要步骤；证据链接可供核对，不承担填补教学断层的任务。

### S7 · 备选是可选择的路径，不是罗列

- Alternative 在声明的适用条件下达成同一个局部成果；Extension 增加新能力。
- 每个重要备选说明适用条件、代价、改变的步骤/配置、增加的依赖、验证方式和返回主线的位置。
- 列少量真正影响用户决策的选项，不追求穷举；没有有价值备选的 Stage 可以不列。
- 把“运行载体”“模型初始化方式”“Agent 架构”分开，不能都当作同层替代。
- 目标或主线明显不同就拆成另一个 Process/Goal，不强塞成一条 Stage 的 Branch。
- 只有方向描述、没有执行路径的内容可以叫 Expansion Map，不应伪装成已完成的操作分支。

### S8 · Example、Practice、迁移检验彼此衔接

- Example 展示对应真实输入与观测结果，非确定性答案注明只是示例。
- Practice 给出完整任务、必要资源、交付产物和验收办法；与参考主线是同一个最小任务或已说明的近邻变体。
- 能力验收与概念问答分开，不能靠填写非空答案证明程序/作品完成。
- 至少有一个近邻迁移任务，检验用户能否判断“换目标/条件后哪里应改、哪里保持”。
- 验证规则有独立依据。不能让同一个生成结果任意决定自己的正确答案，也不能把“没有报错”当作目标达成。

### S9 · 事实、证据、验证状态诚实

- 关键 API、版本语义、默认行为和限制有可核对依据；设计建议与事实分开。
- 引用到真实可解析来源，关键段落可定位；摘要明确标为摘要，不能冒充抓取原文。
- 执行证据包含对象版本/内容标识、环境、验证范围、结果和时间。
- 未验证、服务受限、已失效等情况明确显示，不用模型 confidence 替代证据。
- 不声称一个服务商/操作系统的测试证明所有 provider/环境都成立。
- 不泄露密钥，不让教程中的危险操作或待验证代码直接获得不必要权限。

## 4. 它在用户面前长什么样

### 4.1 三层呈现

```text
第一层：能力地图
  做什么 / 适合谁 / 起点 / 能力目标 / 核心心智模型

第二层：默认主线
  Foundation → Stage 1 → Stage 2 → … → 成果与 Practice

第三层：按需展开
  默认方法 / Concept × Operation / 验收与排错 / 备选 / 证据
```

不是把所有 detail、概念和引用塞进主流程卡片。Main Process 默认保留行动与局部成果；进入 Stage 后立即能找到默认做法，细节和备选按需展开。

### 4.2 一个标准 Stage 的示意

以“创建 Agent”为例，以下是交付形态示意，不是已发布内容或固定 Schema：

```text
Stage：创建 Agent
局部成果：得到配置明确、可调用的 Agent 实例

前置：Foundation 已完成；本项目模型配置已验证
输入：模型配置、tools 列表、system prompt

为什么：把 Model 和工具等组件接入运行 harness
Concept × Operation：Model + Tool → Create → Agent

默认：在 agent.py 中构造 model，再构造 agent
运行：在声明的项目目录执行 python agent.py
输出：本程序中的 agent，交给同一程序的 Invoke 部分
验证：构造成功；模型/工具配置与选择相符
边界：构造成功不等于已完成真实推理或工具调用

备选：模型字符串快捷初始化；何时适用、配置依赖是什么
扩展：需要不同拓扑时进入 LangGraph 扩展，不打断当前主线
排错：版本导入错误 / 配置缺失 / provider 不支持所需能力
证据：本 Case 的 API 版本依据和构造测试记录
```

对于初学者，“输出本程序中的 agent”还必须配合明确文件和代码位置，不能让其误以为终端命令结束后对象会自动保留。

## 5. LangChain 标准样板的目标形态

### 5.1 范围

保留现有五种能力，不扩大成整个 LangChain/LangGraph 生态百科：

1. 创建和调用一个最小 Agent。
2. 使用本地工具并验证完整工具循环。
3. 维护同 thread 的短期对话状态。
4. 用真实本地资料回答问题，验证检索与回答关联。
5. 增加一种真实可观察的执行控制。

声明用户有基础 Python 能力；默认是普通脚本和一个受控、已验证的环境/模型配置。官方服务与第三方网关分支有各自配置说明与验证边界，不把拥有任意 LLM key 当作所有能力都可用。

### 5.2 Shared Foundation

Foundation 不只是“Install LangChain”标题。应包含可打开、可连续完成的任务：

- 创建练习目录，确认 Python 与 shell 的适用条件。
- 创建并激活虚拟环境，安装明确依赖，记录实际版本。
- 配置 key、可选/必要 endpoint 与模型名，明确环境变量和 .env 加载策略。
- 做非敏感配置检查；在授权范围内验证一次真实模型请求。
- 需要工具能力时单独确认 provider 支持 tool calling，不能用纯聊天成功替代。

复用的 Foundation 只需学一次，但每个依赖它的入口都能找到它；换 provider 或版本后相关验证不自动沿用。

### 5.3 一组完整的小任务，而不是 22 个散装片段

| Goal | 默认任务和交付 | 最低验收 | 近邻迁移问题 |
| --- | --- | --- | --- |
| Basic | 一个可重复运行的小脚本，配置明确，创建、调用、检查的是同一程序链 | 同次运行的用户输入与最终 AI 回复；构造与调用区分 | 换 provider 要改什么，换 system prompt 要改什么？ |
| Tools | 本地确定性 lookup/tool；包含 agent 和可观察调用记录 | 核对工具名、参数、工具结果及最终回答关联 | 换成另一种本地工具，哪些部分保持不变？ |
| State | 一个脚本内两轮调用，同 thread 与不同 thread 的对照 | 历史按 thread 隔离；准确解释内存 checkpointer 退出即失效 | 要跨进程保留历史，必须改变什么？ |
| RAG | 本地 notes → 可查询数据 → retrieval tool → agent 回答 | 命中资料事实；来源可追踪；未知问题明确未知；no match 不算 grounded | 从关键词查找换到语义检索，哪部分变、哪些环节不变？ |
| Control | 无破坏性模拟动作，加一种明确的拦截/审批控制 | 正常、拒绝、允许和绕过输入均覆盖；如教审批，须有真实中断/恢复 | 控制工具执行与修改模型提示有什么区别？ |

工具主线选一种本地可确定方案，不偷偷要求第三个天气 API。RAG 主线可以先用简单文本查询，不把 embeddings/vector store 当作所有 RAG 的必备条件；语义检索放到完整备选。

建议先用 Basic + Tools 两个 Goal 试出标准单位，再覆盖全部五个 Goal。不要先把整个 Case 扩写一遍，最后才发现契约设计不合适。

## 6. 质量判定和验证状态

### 6.1 保留原始三层验收含义

| 层级 | 必须证明 | 方法 |
| --- | --- | --- |
| L1 结构 | 引用、起点、前置、主线、分支和产物关系一致 | Schema、引用/依赖/数据流检查、页面导航测试 |
| L2 操作 | 目标用户在声明条件下完成默认任务 | 确定性运行检查、必要的受控真实集成、完整 Process 与 Practice 走查 |
| L3 心智模型 | 用户会解释、排错、选择并迁移到近邻任务 | 有判断标准的解释/诊断题、近邻任务与目标用户观察 |

字段 presence 的检查只是 L1 和部分契约检查，不足以将 L2 / L3 标记为通过。

### 6.2 不用一个“完成”标签混淆事实

建议状态含义：

- 结构合法：只能说明可以存储和展示。
- 标准候选：满足内容契约并经过审查；具体执行/学习验证仍可待办。
- 执行已验证：指定内容版本、路径、环境和 provider 的实际结果已记录。
- 学习已验证：符合声明起点的用户完成任务，并通过近邻迁移检验。

验证应按 Goal/路径记录，不能两个 Goal 测过就将五个全部标为已验证。人工自报进度、模型审查通过、离线测试、真实服务商测试和学习验证属于不同证据，不相互冒充。

“LangChain golden case”应至少覆盖五个 Goal 默认主线和 Practice 的执行验证，并有目标用户的学习验收；未测备选明确列出范围。它不是“整个 LangChain 生态全部正确”的认证。

### 6.3 硬门禁与改进评分分开

硬门禁：阻断执行的错误、缺失关键输入、断裂的产物流、虚假成功判据、关键事实矛盾、伪造引用、验证记录与版本错配。不能被高分的文风或概念覆盖率抵消。

改进评分：目标价值、主线清晰度、概念压缩、解释质量、备选选择价值、迁移能力、认知负荷。沿用原规范 0–3 内部 rubric，不展示伪精确总分。

Fast/Standard/Deep 可改变覆盖范围和细节层次，不得删除使默认路径可执行的配置、输入或验收。快速草稿允许未验证，但必须诚实显示状态。

## 7. 如何稳定生产：从生成文档转为有契约的生产与验收

```text
限定用户/目标/版本/运行边界
→ 获取并整理可靠来源与关键事实
→ 设计能力目标和可观察验收
→ 构建主线及逐步输入输出契约
→ 一致地生成代码/方法、Example、Practice
→ 结构与依赖检查
→ 安全的确定性执行检查
→ 必要的受控真实集成
→ 语义与教学审查
→ 定点修复并重测受影响路径
→ 带验证范围的候选
```

### 7.1 先确定验证问题，再写答案

先明确 Goal 成功与失败条件、固定任务资料和观察方式，再生成实现。测试的核心事实来自可信资料、人工审核的基准或独立规则；生成器不能凭自己的文本任意改动判据使自己过关。

Example 和 Practice 从同一任务、资源和执行方案衍生，不分开凭空写。例如工具命令用 word_count，练习就不能突然要求未提供资源的 weather API。

程序生成的实际输出可以用于更新 Example，但不能修改独立的任务成功条件来迎合错误程序；自然语言输出则做语义与事实检查，不要求逐字匹配。

### 7.2 以 Process 为执行生成与验证单位

各 Stage 共享一份执行计划：文件、对象、配置、输入、输出、验证和分支。写细节时必须携带这份计划，不能让 Stage 各自选不同模型或重建不兼容状态。

运行检查两类路径：

- 从声明起点连续完成完整 Process，检验交接和能力成果。
- 单独进入 Stage 时，入口明确提示其依赖；不能默许变量、文件或授权已存在。

目标或实现变化后，重验依赖它的下游，而不是只检查被编辑的字符串。

### 7.3 工程证据负责工程事实，模型负责需要判断的部分

| 工作 | 主要手段 |
| --- | --- |
| ID / Schema / 引用 / 前置依赖 / 产物关系 | 确定性代码 |
| 语法、导入、文件存在、示例计算、默认执行链 | 隔离运行及独立断言 |
| API、版本、默认行为与关键限制 | 官方/原始资料及相应版本测试 |
| 目标价值、Stage 边界、概念意义、解释与认知负荷 | 基于明确 rubric 的语义审查 |
| 主线是否能被人独立完成、能否迁移 | 声明起点的目标用户验收 |

多角度审查可以由同一模型承担不同检查任务，不必为了角色数量引入多 agent。职责和证据的独立性比“用了几个 reviewer”重要。

### 7.4 执行验证必须有安全边界

不能把模型生成的任意 command 直接放进开发机 shell 自动运行。

设计要求：独立工作目录/隔离环境、资源与超时限制、默认无网络和无宿主凭据、不使用用户数据、依赖来源受控、危险操作阻断。必要网络测试使用明确授权的目标、凭据范围和预算，日志脱敏。

离线库检查和脚本化模型只能证明对应的框架行为，不能假装真实 LLM 推理或 provider 兼容性已验。缺少网络、凭据或执行能力时，保留标准候选与待验项，不编造输出或自动提权。

### 7.5 不只修当前案例，要证明门禁能抓住同类错误

把审查发现做成反例/变异测试：错误转义、空检索数据、无匹配仍成功、状态跨进程丢失、备选无入口、错误 API 断言、批准路径漏测、引用无原文支撑。

必须确认错误版本失败、正确版本通过。只测试一个手工修好的 fixture 会把质量误当成“这份 JSON 正好过关”。

### 7.6 定点修复，有重试上限

质量问题关联 entity_ref、错误类别、可核对证据、建议和受影响下游。按类别修：结构、事实、实现、产物流、验收、教学或 UI。

修复后用原有独立判据重测；内容变化使旧验证失效。重试不改善或资料/环境不足时进入 needs_attention，保留工作与问题，不靠无限重生成保证“全绿”。

### 7.7 质量是版本化资产

保存：输入与设置、来源版本/时间、生成模型与 prompt 版本、Case 内容标识、执行环境、验证范围、测试结果、审查意见和人工修改。

执行记录绑定内容版本/摘要与验证配置；不能为修改后的代码沿用旧通过记录。纯 UI 修改也需重验可达性，但不必无差别重跑所有付费测试。

## 8. 现有 Harness 的最小升级位置

## 9. 最小数据契约，不先建大而全的系统

从样板里验证后，优先结构化以下信息：

- 起点与适用 profile：用户基础、环境、版本、配置要求。
- Stage 输入/输出及前置引用：产物的生成、存放和交接。
- 执行方案：文件或其他交付物、执行上下文、验证步骤。
- Branch 的选择条件、变更内容与回接位置。
- Practice 的资源、交付物、成功/失败判据和迁移任务。
- 验证记录：内容绑定、范围、环境、状态与证据。

先用当前 detail 文本验证最小可读形态；一旦需要机器验证，再正式评审类型与 Schema 版本。不要把新字段随意塞进 additionalProperties，然后假定 prompt、normalizer、assembler、API、UI 和导出都会自动保留。

正式更改应同时覆盖 Schema / 数据模型 / 模型输出契约 / prompts / 归一化 / 装配 / 编辑 / 页面 / 导出 / 质量检查 / 测试。旧发布版本继续可读，新标准通过新候选和新版本应用；不静默改写历史。

验证记录可以先作为版本关联的独立 sidecar/report，而不是迫使旧 Artifact 存入完整日志。是否纳入导出及如何保持便携性，需在样板验证后明确。

## 10. 实施顺序与每阶段的停靠点

| 批次 | 交付 | 进入下一阶段前必须证明 |
| --- | --- | --- |
| A0 标准确认 | 本草案的 MUST、模板、质量 rubric 和验证状态含义 | 产品/内容/工程对“合格”没有相互矛盾的定义 |
| A1 最小标准单位 | Basic + Tools：脚本、Foundation、阶段交接、Practice、证据和备选 | 目标用户能独立完成；验收能抓住错误实现；不会增加无关知识负担 |
| A2 最小契约与展示 | 从样板提炼必要数据字段，打通所有保存和展示链路 | 字段不会丢失；旧版本可读；默认路径和备选入口可达 |
| A3 完整 LangChain 样板 | 覆盖全部五个 Goal，修复既有审查问题，完成受控验证 | 默认主线和 Practice 真正闭合；五个 Goal 的验证范围各自明确 |
| A4 Harness 生产升级 | 执行计划 → 一致生成 → 分层检查 → 定点修复 → 诚实候选 | 多次新生成稳定满足相同标准，不是只会输出手工模板 |
| A5 泛化与回归 | 不同输入、模型/资料条件及其他领域的基准 | 标准不过拟合 LangChain；质量改善不是以误拒率、认知负荷或成本失控为代价 |

本阶段不需要账号、多 provider 路由、学习分析平台或任意代码执行 IDE。先补 COP 交付本身所需的质量能力。

## 11. 如何衡量“稳定”，避免主观宣布

至少分别统计：

- 未经人工改稿的候选首次达标率。
- 有限修复后的达标率及人工介入比例。
- 验证门禁漏掉的关键错误率；错误输入的误接受率。
- 合法路径的误拒率，以及因服务/凭据限制无法验证的比例。
- 目标用户独立完成 Practice 的比例、外部求助位置与首次成果时间。
- 近邻迁移/诊断任务的表现，而不只是 checkpoint 填写率。
- 每份可验收产物的耗时、模型/验证成本和重试次数。

一次成功不能证明稳定。建议初始基准包含 LangChain 的干净从零、第三方配置、部分资源缺失、旧版本资料冲突等场景，再加入 Git、数据可视化或其他不同类型领域；软件执行验证成熟后再验证非软件契约。

LangChain 不应同时充当所有训练样板和全部验收集。保留未用于改 prompt 的输入变体/领域做留出测试；比较不同设置下的独立生成，而不是反复重放相同 fixture。

先取得基线，再制定明确 go/no-go 阈值。可以用每个代表性场景连续 3 次独立生成做最初小样本检查，但这只是回归起点，不是统计意义上的高可靠性证明；应公布样本量、失败类型和验证范围，不给无依据的“99% 高质量”承诺。

## 12. 本轮的决定边界

建议现在确认的是：标准 COP 以能力路径、实际产物和心智模型为中心；LangChain 作为第一个标准样板；稳定生产靠契约、证据和验收闭环，不靠更长 prompt 或更高自评分。

本轮没有自动升级旧项目、改 Schema、执行付费生成或启用模型代码自动运行。后续实现以 A1 的最小样板为起点，新的 Schema 和执行权限单独明确。
