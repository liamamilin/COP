# COP / P Discovery v0.1 — 从任意主题发现用途可能性

> 状态：实验规格。**本阶段的唯一核心交付是可追溯的可能性地图 P Map。** 模板、C/O 图谱延后，不要求先构建完整知识本体。
>
> 产品方向：主题 → 可能性发现 → 去重/补漏 → **事后分类** → 能力地图；随后针对选中的 P 提取可复用模板。
>
> 适用范围：任何*用途边界可界定*的主题（软件、工具、技法或知识领域）。不保证涵盖无限组合的全部可能性。

## 0. 为什么 P Discovery 不是“让模型列 100 个想法”

系统有两种不同结果，必须区别显示：

- **已确认的可能性**：检索得到可信证据，能够把“可实现的结果”追溯到一个具体的官方描述、教程、案例或经人工核实的演示。注意：有 URL 不等于证据确实支持该 P。
- **推测中的可能性**：根据已知机制与组合进行推导，但尚未确认实现方式、版本兼容或工具支持；必须单独待验证，不能与已确认能力混为一谈。

大模型承担语义发现、抽象、归一和补漏；采集、去重规则、证据定位、结构校验由普通程序完成。不要把 prompt 设计当成全部产品能力。

## 1. 输入：先界定主题的用途边界

```json
{
  "topic": "ggplot2",
  "purpose": "用 R 创建静态数据可视化",
  "scope": "ggplot2 官方功能 + 明确注明的常见扩展",
  "audience": "会用 R 的初学者",
  "language": "zh-CN"
}
```

如果只输入“Python”之类的宽泛主题，需要先把它压到可处理的用途范围，例如“Python 数据可视化”或“Python 文件自动化”。不要未经说明就把所有语言用途混在一个地图里。

## 2. P 的三个来源通道

### A. 事实归纳：从现有资料里抽取（主通道）

优先资料：官网 Overview / Guides、API Reference、官方 Cookbook / Examples / Gallery、扩展生态官方索引；其次项目示例、文档教程和可信的真实应用案例；用户问题与常见需求用于发现**缺口**，不直接作为可行性证据。

同一个资料段落可以提取 0～N 个 P。每个候选必须保留 source_id、标题、原文定位与抽取理由。**先抽取 P 候选，不预设类别。**

示例来源：
- ggplot2 官方介绍：<https://ggplot2.tidyverse.org/>
- ggplot2 扩展画廊：<https://exts.ggplot2.tidyverse.org/gallery/>
- LangChain Learn / Use cases：<https://docs.langchain.com/oss/python/learn>

### B. 能力组合：根据已知元素提出新候选（探索通道）

从已确认能力出发，按“对象/数据类型 × 意图/输出 × 视觉表达/操作 × 约束”扩展相邻可能性。这是**产生待验证线索**，不是无依据地宣布支持。

例如，已知可绘图层、分面与多个图形组合时，模型可以提出“在多面板中对比不同群体”“把不同类型图形拼接为报告版面”。下一步必须回到资料或可运行案例确认。

不要生成笛卡尔积的全部组合；过滤不适用、没有用户价值、超出主题边界的组合。

### C. 用户未知：从真实任务倒查可能性（补漏通道）

收集用户提出的目标、Q&A 与典型工作场景，把“我想对比不同群体”映射为候选 P，然后检索证据验证。找不到实现依据的保留为“需求/待验证”，不要冒充支持的 P。

## 3. 首个 MVP 的阶段契约

**D0｜来源集**：输入 Topic + Scope；抓取、解析、去重，保留 URL、访问时间、版本、正文摘录、source_id。可人工放入官方文档以免对搜索 API 依赖过强。

**D1｜多视角候选抽取**（独立结构化 LLM 调用）：分三种视角扫描同一来源集——“用户想得到什么结果”“示例交付了什么产物”“扩展组件增加了什么能力”。每次返回候选 P + source refs；提示词明确禁止输出函数名堆砌、安装步骤、没有结果的抽象名词。

**D2｜归一化与去重**：语义近似候选合并；保留同义词和多处证据；区分“展示两个变量的关系”（用途类别）与“制作散点图”（可做的事），避免混成同一层。统一名称采用**动词 + 可观察成果**，例如“绘制散点图”“按群体拆分图形”“组合两幅独立统计图”。

**D3｜缺口探索**：对比已发现的 P、案例集与能力维度，询问“哪些常见结果还没覆盖？”新候选必须验证证据；缺证据的保留 proposed。

**D4｜事后分类**：等候选集形成后聚类为“变量关系 / 分布 / 群体比较 / 时间变化 / 组合排版”等用途组。允许交叉标签；单一树只是导航视图，不是知识的唯一真相。

**D5｜审核发布**：展示每个 P 的来源、是否为扩展能力、完成结果、适用约束与确认状态。用户可以合并、移动、隐藏、修正。人工审核后的版本才能成为已发布地图。

```text
主题及范围
  → 官方文档 / 示例 / 扩展生态 / 用户场景
  → 多视角 P 候选抽取
  → 去重与归一
  → 发现缺口并验证
  → 事后聚类和分类
  → 可浏览的「可能性地图」
  → [未来] 针对具体 P 提炼多个可复用模板（内含 C/O）
```

## 4. P 候选最小数据契约

本规格先于未来的完整 schema 改动，独立试验：

```json
{
  "id": "p_combine_plots",
  "title": "将两幅独立统计图组合为一个版面",
  "user_intent": "在一张报告图中并排比较两个指标",
  "observable_result": "一个包含两个独立 ggplot 对象的布局",
  "scope_requirement": "需要使用 patchwork 扩展包；不属于 ggplot2 基础包本身",
  "source_ids": ["patchwork-docs"],
  "status": "source_supported",
  "aliases": ["组合图形", "拼接多图"],
  "group_ids": []
}
```

建议状态：`proposed`（模型推导未证实）、`source_supported`（有证据）、`reviewed`（人工核实）。正式 Schema 的状态枚举尚需对齐旧 `candidate` 命名，此处是工作定义，不应提前破坏兼容性。

## 5. 模型调用策略：一次只做一类语义判断

- **抽取提示词**：仅在给出的来源片段里寻找可观察的结果，不预先划分类别；输入 source_id + 段落，输出候选 P、文字依据、范围限制和不确定性。
- **归一提示词**：比较候选，合并同义 P、拆分混合 P，保持每条原始证据和别名；不引入新的可能性。
- **缺口提示词**：拿已有清单与来源覆盖度，提出遗漏的结果，必须返回“需要查证什么”；不得直接将推测写入已确认列表。
- **分类提示词**：只依据已有确认候选做事后聚类，允许多标签、不强制等深的树。
- **审阅提示词**：逐项审核是否满足“一个可理解的结果、当前主题确实支持、来源支持实际断言、类别不混乱”。

每阶段输入、候选、审阅决策需落盘，后续重跑不覆盖人工锁定条目。先把设计验证成立，再接入现有任务队列与 Provider 适配器。

## 6. 两个试验主题与衡量方式

**ggplot2**：从官网和 gallery 发现“绘制散点图、直方图、分面图、组合图（需扩展）”等候选，区分图类型与用途类别，并标识哪些不是 ggplot2 自带功能。

**LangChain Agent**：以当前 Agent 文档和教程为范围，发现“构建工具调用 Agent、返回结构化结果、访问外部检索资源”等用途；不要未经说明把 LangGraph / Deep Agents 全部功能算进 LangChain Agent 基础包。

验收维度：
1. **真实性**：抽样人工核查 P 是否在声明范围内，证据是否直接支持；
2. **覆盖**：与独立人工制作的小型真实用途基准对比遗漏了哪些主要方向；
3. **去重与粒度**：是否大量近义重复或把函数调用当最终目的；
4. **发现价值**：用户能否通过地图找到原本不知道、但能实际完成的事情；
5. **成本**：每份主题的来源量、模型调用数、人工修复成本；不要为提高 P 数量牺牲可信度。

优先实现 **D0–D2 的最小闭环**，然后补 D3–D5；再生成模板。没有可复核来源的提案，不能以“已经证明 COP 的能力发现效果”收尾。

## 7. 不做的事

不声称存在无限完备的 P 清单；不先规定分类体系反推 P；不生成整套 C/O 图谱；不把“最佳实践”变成唯一执行教程；不做无限笛卡尔组合；不承诺大模型自带知识就是可验证来源。
