# Tools 样板任务定义与基准（A1-T01）

日期：2026-10-03（Asia/Shanghai）。状态：**草案已通过 T02–T06 实现验证。** 本文定义 Tools 子样板的具体任务、固定资料、验收判据和迁移任务，为 T02–T08 提供基准。

---

## 1. 任务选择：本地产品目录查询

### 1.1 为什么选择产品目录

- **本地确定性**：查询结果来自固定 JSON 数据，不依赖外部 API 或网络，可重复验证。
- **明确正确值**：每个产品有明确的 name、price、category、in_stock 字段，可以精确核对。
- **需要工具调用**：模型必须从用户问题中提取 product_id，调用工具，使用返回结果构建回答。
- **有边界情况**：未知 product_id、错误类型输入、空值等可以测试错误处理。
- **简单但不平凡**：比纯计算工具更接近真实场景，但不至于复杂到难以验收。

### 1.2 不选择其他方案的理由

- **天气 API**：依赖外部服务，不符合「本地确定性」要求。
- **纯计算器**：不需要工具调用，模型可以直接计算。
- **复杂数据库**：超出 Tools 样板的最小单位目标。
- **第三方业务 API**：增加费用和依赖，不适合教学样板。

## 2. 固定资料与工具定义

### 2.1 产品数据（固定，5 个产品）

```json
{
  "P001": {
    "name": "LangChain 入门教程",
    "price": 99.00,
    "category": "教程",
    "in_stock": true
  },
  "P002": {
    "name": "Agent 开发实战",
    "price": 149.00,
    "category": "教程",
    "in_stock": true
  },
  "P003": {
    "name": "Prompt 工程指南",
    "price": 79.00,
    "category": "电子书",
    "in_stock": false
  },
  "P004": {
    "name": "RAG 系统构建",
    "price": 129.00,
    "category": "教程",
    "in_stock": true
  },
  "P005": {
    "name": "向量数据库对比",
    "price": 59.00,
    "category": "电子书",
    "in_stock": true
  }
}
```

### 2.2 工具定义

**工具名称**：`get_product_info`

**参数**：
- `product_id`（string，必需）：产品 ID，格式为 P001–P005。

**返回**：
- 成功：包含 name、price、category、in_stock 的字典。
- 失败（未知 product_id）：返回 `{"error": "Product not found", "product_id": "<input>"}`。
- 失败（类型错误）：返回 `{"error": "Invalid product_id type", "product_id": "<input>"}`。不抛出异常，与未知 ID 的错误格式保持一致。

**工具说明**（给模型看的 description）：
> 查询产品目录中指定 ID 的产品信息。返回产品名称、价格、分类和库存状态。product_id 必须是 P001 到 P005 之间的字符串。如果产品不存在，返回错误信息。

### 2.3 工具实现要求（T02）

- 使用普通 Python 函数，不依赖 LangChain 或外部库。
- 数据硬编码在函数内或从固定 JSON 文件读取。
- 单元测试覆盖：有效 ID、未知 ID、错误类型、空值。
- 错误处理：不抛出未捕获异常，返回明确的错误结构。

## 3. 已知/未知输入与正确值

### 3.1 已知输入与期望行为

| 用户问题 | 期望 tool_calls | 期望 tool 结果 | 最终回答必须包含的事实 |
| --- | --- | --- | --- |
| "P001 的价格是多少？" | `get_product_info(product_id="P001")` | `{name: "LangChain 入门教程", price: 99.00, ...}` | 产品名称是「LangChain 入门教程」，价格是 99.00 |
| "有没有 Agent 相关的教程？" | `get_product_info(product_id="P002")` | `{name: "Agent 开发实战", price: 149.00, category: "教程", in_stock: true}` | 有「Agent 开发实战」，价格 149.00，有库存 |
| "Prompt 工程指南还有货吗？" | `get_product_info(product_id="P003")` | `{name: "Prompt 工程指南", price: 79.00, in_stock: false}` | 「Prompt 工程指南」库存状态为 false（无货） |
| "最便宜的电子书是什么？" | 可能需要多次调用或模型推理 | 查询 P003 和 P005，比较价格 | 「向量数据库对比」59.00 是最便宜的电子书 |

### 3.2 未知输入与期望行为

| 用户问题 | 期望 tool_calls | 期望 tool 结果 | 最终回答 |
| --- | --- | --- | --- |
| "P999 的价格是多少？" | `get_product_info(product_id="P999")` | `{"error": "Product not found", "product_id": "P999"}` | 明确说明产品 P999 不存在，不能编造信息 |
| "帮我查一下产品 123" | `get_product_info(product_id="123")` | `{"error": "Product not found", "product_id": "123"}` | 明确说明产品 123 不存在 |
| "所有教程的价格" | 多次调用 P001、P002、P004 | 三个产品的完整信息 | 列出三个教程的名称和价格 |

### 3.3 负例（必须拒绝的情况）

- 工具没有被调用，模型直接编造产品信息。
- 工具返回错误，但模型仍然声称产品存在。
- 工具返回 in_stock: false，但模型回答「有货」。
- 模型调用了工具但没有使用返回结果，仍然使用自己的知识回答。

> 注意：模型对价格的格式化（如 99.00 → "99" 或 "99.0"）属于展示层行为，
> 不作为负例。语义判据要求数值一致，允许合理格式化。

## 4. 最终回答验收判据

### 4.1 结构判据（L1/L2）

- 消息序列中包含至少一个 `tool_calls` 消息（role=assistant，包含 tool_calls 字段）。
- 消息序列中包含对应的 `tool` 消息（role=tool，包含 tool_call_id 和 content）。
- 最终 ai 消息的 content 包含工具返回的具体事实（产品名称、价格等）。
- 工具名称必须是 `get_product_info`，参数必须包含 `product_id`。

### 4.2 语义判据（L2/L3）

- 最终回答中的产品名称、价格、库存状态必须与工具返回值一致。
- 如果工具返回错误，回答必须明确说明产品不存在，不能编造。
- 回答必须使用工具返回的事实，不能使用模型自己的知识替代。

### 4.3 独立验收方法

- 从保存的 JSON 中提取 tool_calls 和 tool 消息，核对工具名称、参数、返回值。
- 从最终 ai 消息中提取关键事实，与工具返回值比对。
- 构造错误输入，验证工具返回错误且模型不编造信息。

## 5. 迁移任务

### 5.1 近邻迁移（同一工具，不同问题）

- **任务**：查询一个未在默认问题中出现的产品（如 P004 或 P005）。
- **验收**：模型正确提取 product_id，调用工具，使用返回结果回答。
- **目的**：验证模型不是记忆了默认问题的答案，而是真正理解了工具使用方法。

### 5.2 诊断迁移（错误处理）

- **任务**：查询一个不存在的产品（如 P999）。
- **验收**：工具返回错误，模型明确说明产品不存在，不编造信息。
- **目的**：验证模型能正确处理工具返回的错误，不幻觉。

### 5.3 组合迁移（多次调用）

- **任务**：查询所有教程类产品的价格。
- **验收**：模型调用多次工具（P001、P002、P004），列出所有教程的价格。
- **目的**：验证模型能在一个问题中多次使用工具，整合多个结果。

## 6. 与 Basic 的对比

| 维度 | Basic | Tools |
| --- | --- | --- |
| 消息结构 | human → ai（2 条） | human → assistant(tool_calls) → tool → ai（至少 4 条） |
| 验收重点 | 输入/最终回复链接 | 工具调用/结果/最终回答的因果链 |
| 离线模式 | FakeMessagesListChatModel 返回固定文本 | 需要模拟工具调用和返回 |
| 负例 | 结构错配、输入错配 | 工具未调用、结果未使用、错误未处理 |
| 迁移 | 换问题 | 换产品、错误处理、多次调用 |

**关键区别**：Tools 不能沿用 Basic 的「最终只有 human → ai 两条消息」规则。必须定义匹配 tool calling 能力的消息与行为判据。

## 7. 待确认事项

1. **产品数据是否合适**：当前使用教程/电子书目录，是否需要改为其他领域（如员工目录、设备清单）？
2. **工具名称和参数命名**：`get_product_info` 和 `product_id` 是否清晰？
3. **迁移任务范围**：近邻/诊断/组合三种迁移是否足够？是否需要更多场景？
4. **离线模拟**：如何在离线模式下模拟工具调用？建议方案：构造脚本化消息序列——AIMessage(tool_calls) → ToolMessage → AIMessage(final answer)，与 Basic 的 FakeMessagesListChatModel 思路一致，只是多一层 tool call/response。可在 T06 实现，不阻塞 T02–T05。
5. **验收自动化**：结构判据可以自动化，语义判据是否需要人工判断？能否引入更严格的自动比对？
