## 1. 为什么要做这轮工作

现有 COP Studio 的应用流程与里程碑实现，不能直接证明生成的 COP 是合格的学习工件。LangChain 案例暴露了几类问题：

- Stage 有标题或代码，但缺少完整默认方法、输入、配置、输出交接和独立验收。
- `.env`、key、endpoint、工作目录、对象生命周期等关键条件可能藏在用户需要自行补充的知识里。
- 各 Stage 单独看似合理，连起来却不是同一个可完成的小任务。
- 只有一种写法，或备选只有名称，没有选择条件、可执行方法和回接位置。
- API / 版本事实可能错误；引用存在不等于支持对应事实。
- 打印 created、返回固定 Fake 文本、填写 checkpoint、点击完成，容易被误认成能力已经验证。

所以，这一轮不是继续堆页面或扩写教程，而是建立“什么算合格 → 如何做出样板 → 如何用证据验收 → 如何稳定生产”的闭环。

## 2. Goal：我们最终要达成什么

### 2.1 北极星目标

**让 COP Studio 稳定产出面向明确用户、没有承重隐藏知识、主线简洁可完成、成果可核对、能支持理解和近邻迁移的 COP。**

标准 COP 的工作定义：

> 在声明的用户起点和适用范围内，通过一条默认主线连接关键 Concept 与 Operation，帮助用户做出可观察成果，并能解释、诊断、选择和迁移到相近问题。

这是本项目自己的质量定义，不声称存在唯一的外部“行业标准 COP”。

### 2.2 三个递进目标

| Goal | 成果 | 不算完成的情况 |
| --- | --- | --- |
| G1：定义可验收的标准 COP | 内容要求、交付模板、质量判据、验证状态含义一致 | 只有 Schema 字段、原则口号或模型评分 |
| G2：把 LangChain 做成标准样板 | 五个能力 Goal 各有闭合主线、Practice、证据与明确验证范围 | 只修 Basic、只补 Stage 数量、只跑 Mock 或只把内容展示出来 |
| G3：稳定生产标准 COP | 多次独立生成经有限修复达到同一标准，并在留出输入/其他领域验证 | 手工改好一份 fixture、反复重放同一份案例、一次成功就宣布稳定 |

依赖顺序：G1 指导 G2；G2 验证并修正标准；再把已证明有效的契约和判据应用到 G3。

### 2.3 当前阶段目标

先证明一个最小标准单位成立：**Basic + Tools**。

Basic 的能力成果：用户能以明确配置运行一个普通 Python 脚本，创建无工具 Agent、发送输入、检查同一次真实回复，并解释/修改这条路径。

Tools 的能力成果：用户能让 Agent 使用一个本地确定性工具，核对工具名称、参数、实际返回与最终回答之间的关系，并迁移到一个相近工具任务。

先把这两个单位做闭合，不先重写整套 LangChain，也不先改完所有 Schema / Harness。

## 3. 标准：每份 COP 必须回答什么

| 编号 | 要求 | 核心检查问题 |
| --- | --- | --- |
| S1 | 范围与起点明确 | 适合谁？需要哪些入场能力、资源、版本、权限和网络？哪些不覆盖？ |
| S2 | Goal 是能力成果 | 用户最终交付什么？成功与失败如何观察？ |
| S3 | 默认主线连续 | 从哪里开始？Foundation 能否进入？前一步产物如何成为后一步输入？ |
| S4 | Stage 是闭合局部任务 | 目标、理由、输入、默认操作、输出、验收、恢复是否完整？ |
| S5 | Concept × Operation 有因果关系 | 对哪个对象做了什么，因此发生了什么？ |
| S6 | 没有承重隐藏知识 | 完成主线是否还要自行猜配置、文件、状态、授权或验证方法？ |
| S7 | 备选可选择且能回接 | 何时选？改什么？多什么依赖/代价？如何验证？回到哪里？ |
| S8 | Example / Practice / 迁移衔接 | 是否使用同一任务与资源？能否独立交付并完成相近变化？ |
| S9 | 事实与验证状态诚实 | 来源支持什么？实际测过哪一版、哪条路径？哪些尚未验证？ |

执行原则：

- Keep it simple：简单的是能力路径与理解负担，不是代码字符数越少越好。
- 默认采用目标用户常见且容易复现的方式。软件样板以普通脚本为主；`python -c` 可作小探针，不承担跨进程状态交接。
- 无隐藏知识不等于同时显示所有知识；关键条件要写明或有可达前置入口，细节按需展开。
- 不穷举所有 API / 架构。少量有选择价值的备选即可；扩展新能力时考虑另一个 Goal / Process。
- 概念必要，但不做百科；复制代码有效，但不能代替理解、诊断和迁移。
- 纯解释任务不强行编造命令；可执行任务不能用“阅读一下”替代必要操作。

## 5. Task：可执行任务拆分

任务编号用于交接和记录；以下状态是文档记号，不是新增产品状态枚举。

- **工程通过**：实现及声明范围内的工程检查已完成。
- **待内容审核**：需核对任务价值、主线、概念、信息负担与教学表达。
- **待真实验证**：需明确服务、能力、凭据范围和预算后取得实际结果。
- **待用户验收**：需符合起点的用户独立完成与迁移。
- **未开始 / 待设计**：只有计划，不代表已实施。

## 6. Method：具体怎么开发和验收

### 6.1 每个 Process 的开发循环

```text
定义用户、起点、目标、范围
→ 先确定成果与独立成功/失败判据
→ 核对关键版本事实和可靠来源
→ 设计共享执行计划与 Stage 交接
→ 做最小可运行实现
→ 从同一实现派生 COP、Example、Practice、备选
→ 分层检查、负例与必要的受控真实验证
→ 多角度审查、目标用户独立体验
→ 定点修复并重测受影响路径
→ 保存内容绑定、验证范围和下一步
```

生成单位以完整 Process 为主，不让不同 Stage 各自决定模型、配置、文件名和验收标准。

同时验证两种入口：从声明起点连续走通；单独进入 Stage 时能找到其依赖。目标或产物变化时重验下游，不只看本 Stage 的字符串。

### 6.2 一个任务的交付模板

后续每项任务至少记录：

```text
任务 ID / 所属 Goal / 阶段
要解决的用户问题与局部成果
入场条件、上游依赖、输入与资源来源
默认方法：改哪个文件/对象，在何处执行
Concept × Operation：操作如何造成结果
产物与存放/交接方式
成功条件、失败条件、独立验收方法
常见错误与恢复
重要备选：选择条件、改动、依赖、验证、回接
Example、Practice、近邻迁移问题
事实来源、内容版本/摘要、验证环境/范围/结果
未验项、需要的用户决策、下一任务
```

任务默认包含实现和相称验证，但费用、权限扩张、发布、历史覆盖、破坏性操作须分别满足授权边界。

### 6.3 验证层级与证据

| 层级/证据 | 能证明什么 | 不能替代什么 |
| --- | --- | --- |
| L1 结构与契约 | Schema、引用、依赖、保存、主线/分支可达，声明关系一致 | 内容正确、任务真的做成 |
| 离线工程证据 | 语法/导入、确定性函数、框架管线、文件交接、错误拒绝 | 真实模型推理、provider 兼容性 |
| L2 操作/能力 | 在声明条件下完成默认任务，真实成果与验收一致 | 用户会解释/诊断/迁移 |
| L3 心智模型/学习 | 目标用户能说明因果、选择方案、诊断并完成近邻任务 | 所有其他用户/领域均已有效 |
| 人工自报进度 | 用户报告自己的完成状态 | 上述任何独立验证 |

现有 `quality.py` 的字段/存在性检查很有用，但其“L2/L3 无 issue”不等于真实能力或学习验收通过。课件必须显示验证范围，而不是只有一个总 PASS。

### 6.4 正例、负例、变异测试一起做

除了正确路径通过，还要证明错误路径被拒绝，例如：

- 构造记录冒充实际调用；空回复或输入/answer 错配。
- 状态跨进程丢失；上一 Stage 没有生成下游要求的文件。
- 工具没有被执行、参数错误、结果与最终回答不关联。
- RAG 空资料、无命中却声称 grounded、来源不能支持答案。
- 控制只测拒绝、不测允许/恢复，或可以绕过。
- 备选有标题没有入口；新字段在 normalizer / assembler / 导出中丢失。
- 来源是人工摘要却被展示成原文；验证记录绑定旧代码。

测试判据不能由同一份生成内容任意修改来使自己过关。实际输出可以更新 Example，不能为了错误输出降低 Goal 成功条件。

### 6.5 多角度审核

| 视角 | 重点问题 |
| --- | --- |
| 开发者 | API/版本正确吗？脚本真的能连续执行吗？配置/状态/文件来源明确吗？ |
| 目标用户 | 第一步从哪开始？能否不靠额外搜索完成？错了如何恢复？ |
| 教学/内容 | Goal 有价值吗？概念解释了因果吗？Practice 和迁移检验是否有效？ |
| 产品/UI | 默认主线、当前位置、Foundation、备选、代码、证据和下一步可找到吗？ |
| 安全/运维 | 凭据不泄露吗？费用和请求是否有界？测试隔离、发布边界、历史数据保护是否成立？ |

职责和证据独立比 reviewer / agent 数量重要，不为“多角色”增加无必要编排。

### 6.6 版本化和安全规则

- 保存内容标识/摘要、时间、环境、profile、验证路径、结果、未知项。改内容后旧验证不能自动沿用。
- 当前优先使用独立样板、sidecar 和报告；A2 再评审正式字段与导出。
- Published 不可变；修改走新候选/新版本，发布是用户显式动作。
- 不在文档、日志、截图、代码里保存真实 key；凭据仅由受控私密配置提供。
- 不对任意模型生成代码自动开放宿主网络、凭据、用户文件或无界执行权限。
- 真实验证前明确 provider/endpoint、model、凭据用途、模型请求上限、超时/重试、费用上限；工具循环的一次用户任务可能包含多次模型请求。
- 数据库集成只能使用明确验证过的测试库。该仓库测试 fixture 会 truncate，不能将开发库当测试库；E2E 也不能意外改开发者的共享 provider 设置。
- 无法取得证据时记录待验/受限，不能编造回复、引用、通过结果或静默跳过测试后宣布全绿。
